# AnkiWeb sync research for Ranki

Research only. No application code was changed. Upstream Anki at commit
`be56085c32a9d02b506fa880cfa63c756c1779fc` is the primary source. Version 11 was
rechecked against `ankitects/anki` `main`. Community documents are secondary and
some describe older multipart versions, so they are used only where labeled.

## 1\. Wire protocol

Current sync version is **11** (`SYNC_VERSION_MAX = 11`, named
`SYNC_VERSION_11_DIRECT_POST`). Versions 8 through 10 remain supported by Anki's
server for old clients. Version 11 replaced gzip multipart bodies with zstd and
header fields. See [version.rs](https://github.com/ankitects/anki/blob/be56085c32a9d02b506fa880cfa63c756c1779fc/rslib/src/sync/version.rs).

Default endpoint: `https://sync.ankiweb.net/`. Anki permits a custom endpoint.
AnkiWeb redirects users between sync hosts with HTTP 308, and Anki persists the
new endpoint. Sources are listed in section 9.

Every call is an HTTP POST. The `anki-sync` header contains JSON:

```json
{"v":11,"k":"<host key>","c":"ranki,0.1.0,<build>,<platform>","s":"<random base62>"}
```

`k` is the long-lived host key (`hkey`), empty on login. `s` is a fresh
per-process session key, generated by Anki from a random `u32` in base62. The
legacy multipart format used form fields `k` or `sk` for the host key, `s` for
the session key, `v` for a media client version, and `data` for gzip JSON. In
current media `begin`, the `sk` reply field is the host key again, not a new
media session key. The string `ik` does not occur in current Anki sync source.
Treat it as legacy terminology for a key, not a v11 requirement. Source files
are listed in section 9.

Request bodies are zstd-compressed JSON, except full upload, which is a zstd
frame around raw SQLite bytes. Responses are zstd frames with an
`anki-original-size` header giving the uncompressed length. Empty requests send
`{}`. The reference server caps decompressed payloads at 300 MiB by default (100
MiB times 3) and rejects uploads at or above that limit.

Collection endpoints, all under `sync/`:

| Path | Request | Response |
| --- | --- | --- |
| `hostKey` | `{"u":"user","p":"pass"}` | `{"key":"hkey"}` |
| `meta` | `{"v":11,"cv":"<client version>"}` | metadata object |
| `start` | `{"minUsn":n,"lnewer":bool}` | graves to apply |
| `applyGraves` | local graves | empty |
| `applyChanges` | local notetypes, decks, configs, tags | server changes |
| `chunk` | `{}` | server notes, cards, revlog chunk |
| `applyChunk` | local notes, cards, revlog chunk | empty |
| `sanityCheck2` | local object counts | status and counts |
| `finish` | `{}` | new server modified time |
| `abort` | `{}` | empty |
| `upload` | raw collection bytes | bare `OK` or error text |
| `download` | `{}` | raw collection bytes |

`cv` must follow Anki's `anki,<version>,<platform>` shape. AnkiWeb returns HTTP
400 with body `400` otherwise. Ranki reports `anki,ranki-0.1.0,<platform>`, where
the platform token comes from the build target, so mobile builds report `android`
or `ios`.

Media endpoints under `msync/`: `begin`, `mediaChanges`, `uploadChanges`,
`downloadFiles`, `mediaSanity`. Most media responses use a JSON wrapper with `data`
and `err` fields. Source files are listed in section 9.

`proto/anki/sync.proto` defines the local backend RPC API (`SyncAuth`,
`SyncLoginRequest`, `SyncStatusResponse`). It is not the HTTP wire format. There
is no sync protobuf on the wire in v11.

## 2\. Sequence Anki actually runs

1. Login: POST `sync/hostKey` with `u` and `p`. A 403 means bad credentials.
   Save the returned `key` as `hkey`. The host key is long lived.
2. Status: Anki first checks local `col.mod`, `col.scm`, and last sync stamps.
   If local is clean, POST `sync/meta`. Compare local and remote `mod`, `scm`,
   `usn`, `ts`, and `empty`. A clock difference over 300 seconds aborts. Anki
   treats equal `mod` as no changes, different `scm` as full sync, and otherwise
   as normal delta sync. A 308 on `meta` supplies a new endpoint.
3. Normal sync: `start`, send local graves, apply remote graves, `applyChanges`,
   repeat `chunk` until drained, repeat `applyChunk` until local changes are
   sent, `sanityCheck2`, `finish`. The whole operation runs in one local
   transaction. Failure rolls back and calls `abort`. If sanity counts differ,
   Anki marks the schema changed so the next attempt is a full sync.
4. Full upload: close the collection, read the whole SQLite file, POST
   `sync/upload`. Before upload Anki clears graves and pending `usn` values,
   increments `usn`, bumps `scm`, and sets `ls`. A bare `OK` is success.
5. Full download: POST `sync/download`, stream to a temp file, verify integrity,
   set `col.ls = col.mod`, close, and atomically rename over the old file.
6. Media sync: scan the media folder into a local SQLite media database. POST
   `msync/begin` to learn the server USN, `mediaChanges` with `lastUsn` to get
   `(fname, usn, sha1)` records, `downloadFiles` for up to 25 files per ZIP,
   `uploadChanges` with a ZIP of up to 25 changed or deleted files, then
   `mediaSanity` with the local entry count. A mismatch forces a media resync.

Anki syncs on profile open and close when credentials exist and automatic sync
is enabled. Conflict choices are presented to the user. Sources are listed in section 9.

## 3\. Exchanged data

`meta` fields use short names: `mod` and `scm` are milliseconds, `usn` is an
integer, `ts` is Unix seconds, `msg` is a server message, `cont` says whether to
continue, `hostNum` is deprecated in v11, `empty` means no cards, and
`media_usn` carries the media sequence. Ranki's `col.mod` and `col.scm` are
milliseconds, note and card `mod` are seconds, and revlog ids are milliseconds.

Delta data uses `usn`. Rows with `usn = -1` are local pending changes. Graves
record deletions of cards, notes, and decks. The server assigns a new USN.
Finish increments it and stores the new last sync time. Sources are listed in section 9.

The collection blob is the complete `collection.anki2` SQLite file, not an
`.apkg` or ZIP. Version 11 downloads expect schema 18. Anki accepts valid older
schema files on upload and upgrades them on open. Ranki currently creates
schema 11, so a full download would replace it with schema 18. Ranki's storage
already reads both schemas and leaves schema and collection JSON untouched.

Media is never part of the collection blob. It is a separate folder with a
filename, hash, and USN manifest.

## 4\. Minimal scope and its limits

A minimal Ranki client can implement login, `meta`, full upload, full download,
and local state. This is compatible with the endpoints. It cannot reproduce
Anki's merge behavior. The following checks or behaviors are skipped:

- No `start`, `applyGraves`, `applyChanges`, `chunk`, `applyChunk`, or `finish`.
  If `meta` says normal sync, those server-side pending changes remain. A full
  upload in that state can discard changes made on another device.
- No `sanityCheck2`. Ranki cannot compare object counts before overwriting.
- No media manifest sync. Image and sound changes stay local.
- No `abort`. A failed stateful sync is left to the server timeout.
- No local `usn` preparation before upload. AnkiWeb may accept the file, but
  later syncs can see stale `usn`, `ls`, or `scm` values and force another full
  sync.

Therefore automatic full sync must only run when the direction is provably
safe. Every other case must report a conflict and require an explicit one-way
choice.

## 5\. Authentication

There is no separate public API token in the sync protocol. The host key is the
token. Login still exchanges username and password at `sync/hostKey`. Anki's
backend exposes `sync_login(username, password, endpoint)`, and a 2025 Anki forum
answer confirms the same code path for headless clients.

Anki stores only `syncKey` (hkey), `syncUser`, and endpoint in the profile's
`prefs21.db`. It does not store the password. Home Manager likewise treats the
sync key as a secret file.

Ranki should accept `RANKI_SYNC_KEY` or a `0600` key file, with optional
`RANKI_SYNC_USER` and `RANKI_SYNC_PASSWORD` for one-time login. Never put a
password on the command line. Never log the `anki-sync` header, request bodies,
or URLs with query strings. Anki itself strips URLs from network errors to avoid
exposing keys.

## 6\. Proposed Ranki design

Add a `ranki-sync` crate. Keep `ranki-storage` as the only owner of collection
file handling. Use a blocking HTTP client with zstd support and a fixed timeout,
called from the existing synchronous CLI path. The transport boundary makes
tests independent of AnkiWeb.

```rust
use std::path::{Path, PathBuf};
use std::time::Duration;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum SyncMethod {
    HostKey, Meta, Upload, Download, Abort,
}

#[derive(Clone, Debug)]
pub struct SyncRequest {
    pub method: SyncMethod,
    pub endpoint: String,
    pub host_key: String,
    pub session_key: String,
    pub client_version: String,
    pub body: Vec<u8>, // JSON bytes or raw SQLite bytes
    pub timeout: Duration,
}

#[derive(Clone, Debug)]
pub struct SyncResponse {
    pub status: u16,
    pub body: Vec<u8>, // already decompressed
    pub new_endpoint: Option<String>,
}

pub trait SyncTransport: Send {
    fn request(&mut self, req: SyncRequest) -> Result<SyncResponse, SyncError>;
}
```

`HttpTransport` adds the `anki-sync` header, zstd framing, decompression, and
308 endpoint capture. `MockTransport` returns scripted responses by method and
records requests. Both live behind the same trait.

```rust
#[derive(Clone, Debug, serde::Serialize, serde::Deserialize)]
pub struct SyncState {
    pub version: u8,            // 1
    pub endpoint: String,
    pub host_key: String,
    pub username: Option<String>,
    pub last_mod: Option<i64>,
    pub last_local_mod: Option<i64>,
    pub last_scm: Option<i64>,
    pub last_usn: i32,
    pub last_media_usn: i32,
    pub last_success: Option<i64>,
    pub failures: u32,
}

#[derive(Debug)]
pub enum SyncOutcome {
    Disabled,
    NoChanges,
    Uploaded,
    Downloaded,
    Conflict { reason: String },
    RetryLater { reason: String },
}

pub struct SyncClient<T: SyncTransport> {
    transport: T,
    state: SyncState,
    collection: PathBuf,
    media_dir: PathBuf,
    state_path: PathBuf,
}

impl<T: SyncTransport> SyncClient<T> {
    pub fn new(transport: T, collection: &Path, media_dir: &Path,
               state_path: &Path, credentials: Option<Credentials>)
               -> Result<Option<Self>, SyncError>;
    pub fn sync_once(&mut self) -> Result<SyncOutcome, SyncError>;
    pub fn startup(&mut self) -> SyncOutcome;
    pub fn shutdown(&mut self) -> SyncOutcome;
}
```

`new` returns `Ok(None)` when no credentials exist. `startup` and `shutdown`
become no-ops in that case. The caller supplies the state path inside Ranki's
app data directory. It is written atomically with mode `0600` on Unix and
redacted from diagnostics.

`sync_once` flow:

1. If no hkey and username/password are present, call `hostKey` and save only
   the hkey.
2. POST `meta`. Follow at most 3 redirects. Persist a new endpoint.
3. Reject `cont = false` by surfacing `msg`. Reject `|ts - now| > 300`.
4. If `mod` equals `last_mod`, `col.mod` equals `last_local_mod`, and `scm`
   equals `last_scm`, return `NoChanges`.
5. Decide direction. Download when the local collection is empty and the remote
   one is not. If `last_mod` is known, download when only the remote changed.
   Every other case, including a first sync with data on both sides, returns
   `Conflict` for the user to resolve. `scm` changes always require the same
   decision.
6. For upload, checkpoint and close the collection, clear pending local sync
   state, increment `usn`, set `scm`, set `ls`, read the file, check the 300 MiB
   limit, and POST `upload`. A checkpoint that SQLite reports as blocked is an
   error: the file would otherwise miss rows that are still in the log.
7. For download, POST `download` to a temp file, verify SQLite integrity and a
   valid `col` row, set `col.ls = col.mod`, close, and rename atomically.
8. After either full sync, read `meta` once more and keep that `mod` and `scm`
   as `last_mod` and `last_scm`, with the local `col.mod` as `last_local_mod`.
   `AnkiWeb` stamps its own `mod` when it stores a collection, so the value the
   client sent is not the value the next `meta` reports. Comparing the local
   file against the remote stamp alone would read that re-stamp as a second
   change and report a conflict on every later sync.
9. Clear the failure counter and store the last success time.

Error handling maps HTTP 401 and 403 to `Auth`, 400 to `DatabaseCheck`, 409 to
`Conflict`, 501 to `ClientTooOld`, 5xx to `Server`, 308 to redirect, and
transport failures to `Network` or `Timeout`. Upload replies other than `OK`
become `ServerMessage`.

Retry policy: connect timeout 5 seconds, IO timeout 30 seconds, two retries for
network, timeout, and 5xx errors with 1 and 2 second backoff. No retry for 400,
401, 403, 409, 501, or a started upload. Total budget 2 minutes. Failed
attempts increment `failures` and are retried on the next startup. Shutdown
sync is best effort and uses the same budget.

## 7\. Test strategy

Use `MockTransport` for all state-machine tests. No real credentials, network,
or AnkiWeb account. A scripted `wiremock` or `tiny_http` server can add one test
for header, zstd framing, and `anki-original-size`.

| Case | Mock behavior | Assertion |
| --- | --- | --- |
| login success | `hostKey` returns `{"key":"k"}` | hkey cached, password dropped |
| login failure | `hostKey` returns 403 | `Auth`, no state write |
| full upload | `meta` remote empty, `upload` returns `OK` | closed collection sent, state updated |
| full download | `meta` local empty, `download` returns a valid copy | temp validated, atomic replace |
| conflict | both sides changed | `Conflict`, no write |
| offline retry | first `meta` times out, next succeeds | two retries, `RetryLater` then success |
| no credentials | no hkey, no username | `Disabled`, no request |

Add guard tests for corrupt download bytes, oversized upload, clock skew,
sanity of local USN preparation, and state file permissions.

## 8\. Security and data-loss guards

- Never overwrite a newer local collection. Require last-sync stamps and refuse
  a one-way sync when both sides changed.
- Checkpoint WAL and close the SQLite connection before reading. Ranki already
  has `Collection::checkpoint` and `Collection::close`. Do not copy only
  `collection.anki2` while a writer is active.
- Write downloads to a temp file in the same directory, validate it, then
  rename. Keep the old file on any failure.
- Do not delete media during a collection-only sync. Media deletions need a
  fully synced manifest, as the Anki manual warns.
- Preserve `notes.guid`, `col.crt`, and schema metadata. Do not rewrite schema
  11 config JSON as if it were schema 18.
- Keep credentials out of argv, logs, errors, and version control. Use `0600`
  state files and atomically replace them.
- Abort on clock skew over 300 seconds and on server `cont = false`.
- Back up the local collection before the first full download.
